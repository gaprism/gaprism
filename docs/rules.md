# Rules

> Generated from the code by `uv run python -m app.rules.docs`. Change a rule in `app/rules/`
> and regenerate; do not edit this file by hand (a test fails when it is out of date).

A **rule** is a pure function: stored check results in, findings out. It never touches the network
or the database. The checks collect facts; the rules judge them. That keeps judgements testable
with recorded data and lets a rule be refined and re-run over old scans
(`flask findings evaluate`).

## What a finding carries

- **Severity** — how bad it is if true: Critical, High, Medium, Low or Informational. The current
  rules produce High and below; Critical is reserved.
- **Confidence** — how sure we are that it is true: high, medium, low or unknown. It is separate
  from severity: a CDN edge outside the allowed area is a Medium finding with low confidence.
- **Attribution** — whose it is: *confirmed for the hostname*, *seen on the address only*,
  *shared infrastructure* (an address many tenants use) or *the whole domain*. An address is not a
  hostname; findings say which one they rest on.
- **Evidence** — the ids of the check results the decision is based on. A finding points at its
  evidence; it does not copy it.
- **Fingerprint** — `sha256(rule id | subject)`. It does not change with severity, parameters or the
  rule's version, so a decision about a finding (accepting it, S2.6) still applies after a re-scan
  and after the rule is refined.

**No finding is not a clean bill of health.** A check that failed, timed out or found nothing gives
a rule nothing to read, and nothing to read is never a finding. The pages say so next to the
findings, and report which checks did not complete.

## Settings

- `DATA_LOCATION_ALLOWED` — ISO country codes an address may be located in (rule
  `LOCATION_OUTSIDE_EU_CH`). Default: the EU-27, the EEA (IS, LI, NO) and CH.
- `BREACH_RECENT_MONTHS` — a public breach newer than this is High, an older one Medium (rule
  `PUBLIC_BREACH_HISTORY`). Default: 24.

## Adding a rule

One function in `app/rules/host.py`, `ip.py` or `domain.py` with the `@host_rule`, `@ip_rule` or
`@domain_rule` decorator (id, title, one-sentence message with `%(name)s` placeholders, advice, a
description of when it fires, the severities it can produce, the checks it reads and the labels of
its facts). Add a test in `tests/rules/` that feeds it the output of the real check, and regenerate
this file. Wording changes keep the rule's version; a change in *what* it flags raises it.

## Host rules

Run once per host of the scan, over what that host's checks collected.

### `TLS_INVALID`

**Certificate not valid** · High or Medium · reads the `tls` check · version 1

*Fires when:* The certificate was read but fails validation: expired, not yet valid, not trusted or issued for another name.

*Says:* The TLS certificate of {host} is not valid for clients: {failures}.

*Advice:* Ask the vendor to replace the certificate and to monitor expiry and names.

*Facts shown:* Problems, Days remaining

### `TLS_EXPIRES_SOON`

**Certificate expires soon** · Medium or Low · reads the `tls` check · version 1

*Fires when:* A valid certificate expires within 30 days (Medium within 7 days).

*Says:* The TLS certificate of {host} expires in {days} days.

*Advice:* Renewal should be automated; ask how certificate expiry is monitored.

*Facts shown:* Days remaining, Expires

### `TLS_WEAK_KEY`

**Weak certificate key** · High · reads the `tls` check · version 1

*Fires when:* The certificate's key is RSA below 2048 bits, elliptic-curve below 224 bits, or DSA.

*Says:* The certificate of {host} uses a weak {key_type} key ({key_bits} bits).

*Advice:* Keys should be RSA with 2048 bits or more, or elliptic-curve (P-256 or better).

*Facts shown:* Key type, Key size (bits)

### `TLS_WEAK_SIGNATURE`

**Weak certificate signature** · High · reads the `tls` check · version 1

*Fires when:* The certificate is signed with SHA-1 or MD5 (or older).

*Says:* The certificate of {host} is signed with the weak algorithm {algorithm}.

*Advice:* Certificates must be signed with SHA-256 or stronger.

*Facts shown:* Signature algorithm

### `TLS_LEGACY_PROTOCOL`

**Outdated TLS versions accepted** · Medium · reads the `tls_protocols` check · version 1

*Fires when:* The server completed a handshake in which only TLS 1.0, or only TLS 1.1, was offered and also accepts TLS 1.2 or TLS 1.3. RFC 8996 retired both old versions in 2021, and frameworks such as PCI DSS and NIST SP 800-52 rev. 2 no longer allow them. A server that accepts nothing newer is reported by TLS_NO_MODERN_PROTOCOL instead.

*Says:* {host} still accepts {versions} next to the current versions. TLS 1.0 and 1.1 were retired in 2021 (RFC 8996).

*Advice:* Switch off TLS 1.0 and TLS 1.1 so that only TLS 1.2 and TLS 1.3 are accepted.

*Facts shown:* Outdated versions accepted, Current versions accepted

### `TLS_NO_MODERN_PROTOCOL`

**Only outdated TLS versions accepted** · High · reads the `tls_protocols` check · version 1

*Fires when:* The server completed a handshake with TLS 1.0 or TLS 1.1 and answered both TLS 1.2 and TLS 1.3 with a refusal. A question that timed out or could not be put does not count as a refusal.

*Says:* {host} accepts {versions} and refuses TLS 1.2 and TLS 1.3: current browsers and libraries cannot connect securely.

*Advice:* Enable TLS 1.2 and TLS 1.3 and switch off TLS 1.0 and TLS 1.1.

*Facts shown:* Versions accepted

### `TLS_NO_TLS13`

**TLS 1.3 not offered** · Informational · reads the `tls_protocols` check · version 1

*Fires when:* The server accepted a TLS 1.2 handshake and answered a TLS 1.3 handshake with a refusal. An observation, not a weakness: TLS 1.2 with good suites is still sound.

*Says:* {host} accepts TLS 1.2 but not TLS 1.3.

*Advice:* Enable TLS 1.3 when the server software supports it: it is faster and drops the weak options of older versions. Not urgent.

*Facts shown:* Versions accepted

### `TLS_NULL_OR_ANONYMOUS_SUITES`

**Suites without encryption or authentication accepted** · High · reads the `tls_protocols` check · version 1

*Fires when:* The server completed a handshake in which only suites without encryption (NULL) or without authentication (anonymous) were offered.

*Says:* {host} accepts the cipher suite {cipher}, which has no encryption or no authentication of the server.

*Advice:* Remove NULL and anonymous cipher suites from the server's configuration: with them traffic can be read, or anyone can pose as the server.

*Facts shown:* Suite it chose

### `TLS_NO_FORWARD_SECRECY`

**Suite without forward secrecy chosen** · Low · reads the `tls_protocols` check · version 1

*Fires when:* Offered a normal list of suites in a TLS 1.2 handshake, the server chose one whose key exchange is not ephemeral (not ECDHE or DHE). That it merely *accepts* such a suite when nothing better is offered is common and not reported.

*Says:* In a TLS 1.2 handshake {host} chose {cipher}, a suite that gives no forward secrecy, although better ones were offered.

*Advice:* Put the ECDHE suites first in the server's preference order, so that a stolen server key cannot open recorded sessions.

*Facts shown:* Suite it chose

### `NO_HTTPS`

**No HTTPS** · High · reads the `http` check · version 1

*Fires when:* HTTPS could not be reached (nothing listening, no answer) while plain HTTP answered.

*Says:* {host} answers on plain HTTP but offers no HTTPS.

*Advice:* Ask the vendor to serve the site over HTTPS only.

*Facts shown:* Why HTTPS failed

### `HTTP_NO_HTTPS_REDIRECT`

**HTTP is not redirected to HTTPS** · Medium · reads the `http` check · version 1

*Fires when:* HTTPS works and plain HTTP (port 80) answers without redirecting to HTTPS.

*Says:* {host} serves content over plain HTTP instead of redirecting to HTTPS.

*Advice:* Port 80 should redirect to HTTPS (or be closed).

*Facts shown:* Status on port 80

### `HSTS_MISSING`

**HSTS not set** · Low · reads the `http` check · version 1

*Fires when:* An HTTPS response of the host itself has no Strict-Transport-Security header.

*Says:* {host} does not send a Strict-Transport-Security header.

*Advice:* Send Strict-Transport-Security so browsers stay on HTTPS.

### `HSTS_WEAK`

**HSTS lifetime is short** · Informational · reads the `http` check · version 1

*Fires when:* Strict-Transport-Security is set but its max-age is under six months.

*Says:* The Strict-Transport-Security lifetime of {host} is {max_age} seconds.

*Advice:* Use a max-age of at least six months (15552000 seconds).

*Facts shown:* max-age (seconds)

### `CSP_MISSING`

**No Content-Security-Policy** · Low · reads the `http` check · version 1

*Fires when:* An HTML response of the host itself has no Content-Security-Policy header.

*Says:* {host} does not send a Content-Security-Policy header.

*Advice:* A Content-Security-Policy limits the damage of injected scripts.

### `XCTO_MISSING`

**No X-Content-Type-Options** · Low · reads the `http` check · version 1

*Fires when:* An HTML response of the host itself has no X-Content-Type-Options header.

*Says:* {host} does not send X-Content-Type-Options: nosniff.

*Advice:* Send X-Content-Type-Options: nosniff so browsers do not guess content types.

### `FRAME_PROTECTION_MISSING`

**No clickjacking protection** · Low · reads the `http` check · version 1

*Fires when:* An HTML response has no X-Frame-Options header and no frame-ancestors in its CSP.

*Says:* {host} sets neither X-Frame-Options nor a CSP frame-ancestors directive.

*Advice:* Forbid framing with X-Frame-Options or Content-Security-Policy: frame-ancestors.

### `COOKIE_INSECURE`

**Session cookie without protection flags** · Medium · reads the `http` check · version 1

*Fires when:* A cookie whose name looks like a session or token lacks Secure (on HTTPS) or HttpOnly (CSRF tokens are exempt from HttpOnly). Cookie values are never stored.

*Says:* {host} sets session-like cookies without the Secure or HttpOnly flag: {cookies}.

*Advice:* Session cookies should be Secure and HttpOnly (and carry a SameSite attribute).

*Facts shown:* Without Secure, Without HttpOnly

### `SERVER_VERSION_DISCLOSED`

**Software version disclosed** · Informational · reads the `http` check · version 1

*Fires when:* The Server or X-Powered-By header contains a version number.

*Says:* {host} reveals software versions in its response headers: {versions}.

*Advice:* Hide version numbers from Server and X-Powered-By; they help attackers.

### `TECH_OUTDATED_VERSION`

**Old software version** · Low · reads the `tech`, `http` checks · version 1

*Fires when:* The technology check read the version of a product that the small own ruleset has dates or known flaws for, and that version is past its upstream end of life (PHP, IIS, Drupal, Joomla, Apache 2.2 and older, AngularJS 1.x, Bootstrap 4 and older, Python 2) or has well-known vulnerabilities (jQuery before 3.5). The version comes from a response header, the generator tag or the name of a file the page loads. Always Low: whether a flaw can be used depends on how the software is used, and the known vulnerabilities of services are the ports check's business. Confidence is Medium when the page shows the version (generator tag, file name) and Low when only a server header does, because distributions fix flaws without changing the number. A product the ruleset has no dates for is not judged: no finding is no statement that the software is current.

*Says:* {host} shows software that is old: {outdated}.

*Advice:* Find out which version really runs and whether it still receives security fixes, and update what has reached its end of life. A version that only a server header or a file name shows can be patched without changing the number, or be wrong, so ask rather than assume.

*Facts shown:* Software, What is known, Version read from

### `SCRIPT_FROM_COMPROMISED_HOST`

**Page loads from a host that served malware** · High or Medium · reads the `tech`, `http` checks · version 1

*Fires when:* The first page of the host names a host that the ruleset lists as having served malicious code to the pages that load from it (the polyfill.io supply chain attack of 2024 and the networks of hosts that belong to the same campaign). High with Medium confidence when a script or a frame loads from it: the page was seen to hand the visitor's browser over, but whether the host still serves the malicious file is not known (several were taken down). Medium with Low confidence when only a style sheet, an image, a form or an inline script names it. Only what the first page shows is read: scripts that load other scripts are not followed.

*Says:* {host} loads content from {flagged}, which is known to have served malicious code to the visitors of the pages that load from it.

*Advice:* Remove the reference, or replace it with a copy of the file that the site serves itself or with a trusted mirror, and review what the page loaded in the meantime. Whoever controls such a host can run code in every visitor's browser.

*Facts shown:* Hosts, Loaded as

### `HOST_BLOCKED_BY_SECURITY_DNS`

**Blocked by security DNS resolvers** · High or Medium · reads the `reputation`, `dns` checks · version 1

*Fires when:* A security DNS resolver (Quad9, Cloudflare's malware-blocking 1.1.1.2) refuses a name that the DNS check resolved: it says so with an Extended DNS Error (Blocked, Censored, Filtered, Prohibited), answers NXDOMAIN or answers 0.0.0.0. Medium when one resolver blocks it, High when two agree. The confidence is Medium: blocking is a third party's classification, which can be wrong or can list a name because of what another tenant of a shared host did. A resolver that failed, did not answer, or answered differently without saying why is not counted as a block, and a name that is not blocked is no proof that it is clean: each resolver knows only part of the bad names of the internet.

*Says:* {host} is blocked by {blocked_by}, which refuse names that their threat intelligence flags as malicious.

*Advice:* Find out what the host serves and who controls it: a compromised site, a taken-over subdomain or a phishing page under the vendor's name are all possible. Ask the vendor whether they know. If the name is blocked by mistake, the resolvers' operators have a way to ask for a review.

*Facts shown:* Blocked by, How it shows, Resolvers asked

### `HOST_ON_BLOCKLIST`

**Host name on a blocklist** · High · reads the `blocklists`, `dns` checks · version 1

*Fires when:* The host's own name is on a list that `flask datasets update` installed: the abuse.ch URLhaus host file (hosts of malware URLs that are active or were added in the last 48 hours) or the Phishing.Database list of phishing hosts that still answered when they were tested. High, with Medium confidence: a list is a third party's classification, a host name can be listed because of one page of a site, and an entry can outlive the problem until the list is updated. The finding names each list with the day it was downloaded. A list that is not installed or cannot be read gives the rule nothing to read, and a name that is not listed is no proof that it is clean: the lists hold only what their maintainers have seen.

*Says:* {host} is listed by {lists} for {listed_for}.

*Advice:* Find out what the host serves and who controls it: a compromised site, a taken-over subdomain or a phishing page under the vendor's name are all possible. Ask the vendor whether they know and what they did about it. A listing can be out of date or mistaken; the maintainers of the list have a way to ask for a review.

*Facts shown:* Listed by, Listed for

### `ALIAS_ON_BLOCKLIST`

**Alias of a blocklisted host** · Medium · reads the `blocklists`, `dns` checks · version 1

*Fires when:* A name that the host is an alias for (a CNAME target) is on a list that `flask datasets update` installed, while the host's own name is not. Medium, with Medium confidence: the list names the target, and a server often answers differently under another name, so what the vendor's host serves is not known. A list that is not installed or cannot be read gives the rule nothing to read, and a name that is not listed is no proof that it is clean.

*Says:* {host} is an alias for {listed}, which is listed by {lists} for {listed_for}.

*Advice:* Ask the vendor why the name points there. An alias to a host that serves malware or phishing is either a leftover that someone else has since taken over, or a sign that the vendor's DNS was changed. Remove the alias if nothing needs it. What the listed host serves under this name is not known.

*Facts shown:* Listed alias, Listed by, Listed for

### `HOST_ADDRESS_ON_BLOCKLIST`

**Address on a blocklist** · High or Medium · reads the `blocklists`, `dns` checks · version 1

*Fires when:* One of the host's public addresses is on a list that `flask datasets update` installed: the abuse.ch Feodo Tracker list of botnet command-and-control servers, the Phishing.Database list of phishing addresses or an address in the URLhaus host file. High when a botnet or malware list names it (Medium confidence), Medium when only the phishing list does (Low confidence: shared hosting puts many sites on one address). An address of a CDN or other shared edge never raises it, however it is listed: the listing can come from any of the sites behind it. The finding belongs to the address, not to the host name. A list that is not installed or cannot be read gives the rule nothing to read, and an address that is not listed is no proof that it is clean.

*Says:* {host} resolves to {addresses}, which is listed by {lists} for {listed_for}.

*Advice:* Find out whether the address is the vendor's own server or shared with others. An address that a botnet or malware list names can mean that the server behind it is compromised; one on a phishing list may belong to a neighbour on shared hosting. Ask the vendor to look at the server.

*Facts shown:* Listed addresses, Listed by, Listed for

### `DANGLING_CNAME`

**Alias points nowhere** · Medium · reads the `dns`, `takeover` checks · version 2

*Fires when:* The CNAME chain of the host ends in a name that does not exist. Whether anyone can claim that name is not known for a service the takeover check does not list, so confidence is low. When the name belongs to a service where anyone can register it (Azure, Elastic Beanstalk, ...), TAKEOVER_LIKELY reports it instead, and this rule stays silent.

*Says:* {host} is an alias for {target}, which does not exist; if the target can be claimed, the name can be taken over.

*Advice:* Remove the alias, or check that the target cannot be registered by someone else.

*Facts shown:* Missing target

### `TAKEOVER_LIKELY`

**Alias may be taken over** · High · reads the `takeover`, `dns` checks · version 1

*Fires when:* The host is an alias (CNAME) for a hosted service whose names a stranger can claim (GitHub Pages, Heroku, Amazon S3, Netlify, Vercel, Surge, Pantheon, Tilda, Azure, Elastic Beanstalk, Discourse), and the name behind the alias shows as unclaimed: the target does not exist and the service lets anyone register it, or the service answers the host with its own page for a name nobody has claimed (the status and the text the service shows for it). Whoever claims the name serves content on the vendor's host name, so the severity is High either way. Confidence is High when anyone may claim the name and the page was seen, Medium when the service checks something first (an account, a verified domain) or when only the missing name was seen. Nothing is claimed or tried beyond the request a visitor sends; a page that could not be read is no finding (the check says that it did not test).

*Says:* {host} is an alias for {target} at {service}, and the name behind it looks unclaimed: {takeover_how}.

*Advice:* Remove the DNS record if the alias is no longer needed, or create the resource at the service again before somebody else does. Ask the vendor how its aliases are reviewed when a service is switched off.

*Facts shown:* Service, Alias for, How it shows, HTTP status, The page says, Can a stranger claim the name?, Also an alias for

### `DNS_PRIVATE_ADDRESS`

**Public name points to a private address** · Low · reads the `dns` check · version 1

*Fires when:* The host's A or AAAA records contain private, loopback or link-local addresses.

*Says:* {host} resolves to non-public addresses: {addresses}.

*Advice:* Public DNS should not publish internal addresses; they reveal the network layout.

### `LOCATION_OUTSIDE_EU_CH`

**Host located outside the allowed area** · High or Medium · reads the `ip` check · version 1

*Fires when:* A public address of the host is located (by country) outside the allowed area (EU-27, EEA and CH by default, `DATA_LOCATION_ALLOWED`). Addresses of CDN or anycast networks show an edge location, not the data centre: when only those are outside the finding is Medium with low confidence. Addresses of large cloud providers are often registered in a country other than the region they run in, so confidence is medium there.

*Says:* {host} resolves to an address located in {countries}, outside the allowed area.

*Advice:* Ask the vendor where the data is processed and stored; the address location is only a first indication.

*Facts shown:* Countries, Addresses

## Address rules

Run once per public address a scanner reported on, however many hosts resolve to it; the finding lists those hosts. Addresses of shared infrastructure (CDN edges, multi-tenant hosting) are skipped: what is open there says nothing about the vendor.

### `RISKY_PORT_EXPOSED`

**Risky service reachable from the internet** · High or Medium · reads the `ports` check · version 1

*Fires when:* A port of a risky service (FTP, SSH, Telnet, SMB, RDP, MySQL, PostgreSQL, Redis, Elasticsearch, Memcached, MongoDB) was observed open. High for databases, remote administration and file sharing, Medium for FTP and SSH. The data is a scanner's snapshot, so confidence is medium. Addresses of shared infrastructure are skipped.

*Says:* A scanner saw {service} (port {port}) open on {ip}.

*Advice:* Databases, remote administration and file sharing should not be reachable from the internet; ask the vendor to restrict them.

*Facts shown:* Hosts on this address, Product, Version

### `CVE_OBSERVED`

**Known vulnerabilities reported** · High or Medium or Low or Informational · reads the `ports` check · version 2

*Fires when:* The provider lists CVE identifiers for the address (it derives them from software versions it read, so they are leads, not proof). The severity follows what is known about the exploitation of those CVEs: High when one is on CISA's Known Exploited Vulnerabilities list, Medium when the highest EPSS score is 0.5 or more (an estimated chance of exploitation within 30 days of 50 %), Low from 0.1, otherwise Informational. When the exploitation data is not installed the finding stays Informational and says that it was not ranked. Confidence is Medium when the provider verified a CVE, otherwise Low. Addresses of shared infrastructure are skipped.

*Says:* {count} CVEs are reported for software seen on {ip}; they are leads to verify, not confirmed vulnerabilities.

*Advice:* Ask the vendor which of these apply and how patching is tracked, starting with the ones that are known to be exploited.

*Facts shown:* Examples, Known to be exploited (CISA KEV), Used in ransomware campaigns, Highest EPSS score, Highest CVSS score, Ranked by, Exploitation data out of date, Hosts on this address

## Domain rules

Run once per scan, over the checks of the domain itself.

### `SPF_MISSING`

**No SPF record** · Medium or Low · reads the `email` check · version 1

*Fires when:* The domain has no SPF record. Medium if it has mail servers, Low if it does not (a domain without mail can still be spoofed).

*Says:* {domain} publishes no SPF record, so receivers cannot tell forged mail from real.

*Advice:* Publish an SPF record; a domain that sends no mail should say so with `v=spf1 -all`.

### `SPF_PERMISSIVE`

**SPF does not restrict senders** · High or Medium · reads the `email` check · version 1

*Fires when:* The SPF record ends in `+all` (High: anyone may send), in `?all` or has no `all` or redirect at all (Medium: neutral, no protection).

*Says:* The SPF record of {domain} ends in {ending}, which does not tell receivers to reject mail from other senders.

*Advice:* End the record with `-all` (or `~all` while rolling it out).

*Facts shown:* Record ends in

### `SPF_INVALID`

**SPF record is broken** · Medium · reads the `email` check · version 1

*Fires when:* There is more than one SPF record, or evaluating it needs more than 10 DNS lookups; receivers treat both as an error, so the record protects nothing.

*Says:* The SPF record of {domain} is invalid for receivers: {problems}.

*Advice:* Publish a single SPF record that needs at most 10 DNS lookups.

*Facts shown:* Problems, DNS lookups

### `DMARC_MISSING`

**No DMARC record** · Medium or Low · reads the `email` check · version 1

*Fires when:* The domain has no DMARC record. Medium if it has mail servers, Low if it does not.

*Says:* {domain} publishes no DMARC policy, so receivers have no instruction for forged mail.

*Advice:* Publish a DMARC record, starting with `p=none` and reporting, then move to `reject`.

### `DMARC_POLICY_NONE`

**DMARC only monitors** · Low · reads the `email` check · version 1

*Fires when:* A DMARC record exists with `p=none`.

*Says:* The DMARC policy of {domain} is `none`: forged mail is reported but still delivered.

*Advice:* Once the reports look clean, move the policy to `quarantine` and then `reject`.

*Facts shown:* Aggregate reports sent to

### `DMARC_INVALID`

**DMARC record is broken** · Medium · reads the `email` check · version 1

*Fires when:* A DMARC record exists but has no valid policy, or there is more than one record.

*Says:* The DMARC record of {domain} is not valid, so receivers ignore it: {problems}.

*Advice:* Publish a single DMARC record with a valid `p=` policy.

*Facts shown:* Problems

### `MTA_STS_MISSING`

**No MTA-STS policy** · Informational · reads the `email` check · version 1

*Fires when:* The domain has mail servers and no MTA-STS record.

*Says:* {domain} receives mail but publishes no MTA-STS policy, so mail can be downgraded in transit.

*Advice:* Publish an MTA-STS policy (and TLS-RPT reporting) so senders insist on TLS.

### `DNSSEC_NOT_ENABLED`

**DNSSEC is not enabled** · Informational · reads the `registration` check · version 1

*Fires when:* The registry reports that the delegation is not signed.

*Says:* The domain {domain} is not signed with DNSSEC.

*Advice:* DNSSEC protects DNS answers from forgery; ask whether it is planned.

### `DOMAIN_EXPIRES_SOON`

**Domain registration expires soon** · High or Medium · reads the `registration` check · version 1

*Fires when:* The registry's expiry date is within 30 days (Medium) or has passed (High). Registries that publish no dates (such as .ch) cannot be judged.

*Says:* The registration of {domain} runs out on {expires} (days left: {days}).

*Advice:* Ask whether auto-renewal is on and who is responsible for the registration.

*Facts shown:* Days left, Expires

### `DOMAIN_RECENTLY_REGISTERED`

**Domain registered recently** · Informational · reads the `registration` check · version 1

*Fires when:* The registration date is less than 90 days ago.

*Says:* {domain} was registered {age} days ago.

*Advice:* A young domain has no track record; check who the vendor is before relying on it.

*Facts shown:* Registered

### `DOMAIN_NOT_LOCKED`

**Domain has no transfer lock** · Low · reads the `registration` check · version 1

*Fires when:* The registry publishes EPP status flags but none of them forbids a transfer. Registries that publish no lock concept are not judged.

*Says:* {domain} can be transferred to another registrar without a lock in the way.

*Advice:* Ask the registrar to set the transfer lock (clientTransferProhibited).

*Facts shown:* Status flags

### `PUBLIC_BREACH_HISTORY`

**Public breach on record** · High or Medium · reads the `breaches` check · version 1

*Fires when:* Have I Been Pwned documents a breach of a service on the domain. Fabricated entries, spam lists and retired breaches are ignored. Medium; High if the breach happened within `BREACH_RECENT_MONTHS` (24 by default). One finding per breach, so each can be accepted on its own.

*Says:* Have I Been Pwned lists a breach of {domain}: {title} ({breach_date}).

*Advice:* Ask what happened, what was done about it and whether the data was protected (for example hashed passwords).

*Facts shown:* Accounts, Data exposed, Verified by HIBP, Months ago

### `SECURITY_TXT_MISSING`

**No security.txt** · Informational · reads the `security_txt` check · version 1

*Fires when:* Neither /.well-known/security.txt nor /security.txt was found.

*Says:* {domain} publishes no security.txt, so there is no stated way to report a vulnerability.

*Advice:* Publish /.well-known/security.txt (RFC 9116) with a contact and an expiry date.

### `SECURITY_TXT_INVALID`

**security.txt is unusable** · Low · reads the `security_txt` check · version 1

*Fires when:* A security.txt was found but has no contact, no valid or a repeated Expires field, or has expired.

*Says:* The security.txt of {domain} has problems: {problems}.

*Advice:* Keep security.txt current: a contact, a future expiry date, one Expires field.

*Facts shown:* Problems, Found at

### `CAA_MISSING`

**No CAA records** · Informational · reads the `domain_dns` check · version 1

*Fires when:* No CAA record exists at the domain or any parent name up to its zone.

*Says:* {domain} has no CAA records, so any certificate authority may issue for it.

*Advice:* Publish CAA records naming the certificate authorities you use.

### `NS_NOT_REDUNDANT`

**Name servers are not redundant** · Medium or Low · reads the `domain_dns` check · version 1

*Fires when:* Fewer than two name servers (Medium), all servers in one network, or a server without an address (Low). One DNS operator alone is not a finding: the large providers are redundant by design.

*Says:* The name servers of {domain} are not redundant: {problems}.

*Advice:* Use at least two name servers in different networks.

*Facts shown:* Problems, Name servers
