# Checks catalogue — what we check, and with which free data

> Proposed 2026-10-04. Built from a review of all 38 web-check handlers (`Lissy93/web-check`, MIT) and a live probe of the candidate free sources on 2026-10-04. Roadmap stories reference the IDs below.
> **Answers:** **W** = Where is the data? · **P** = Who processes it? · **S** = How secure is the external posture?

## 1. Checks we will build

**Shipped:**
- **C01 DNS** (S1.6, 2026-10-04): A, AAAA, the explicit CNAME chain (with a `dangling_cname` flag when the last target does not exist), MX, NS, TXT and CAA, each with its TTL, asked of `EGRESS_DNS_RESOLVERS` (default 1.1.1.1 and 8.8.8.8; `system` uses the operating system's resolver). Every address is screened with the egress gate's rules: non-public answers are listed under `blocked` with a reason (private, loopback, link-local, …) and never reach a check that connects; `addresses` holds the usable public ones. NXDOMAIN is `no_data`; a name that exists but has no records is `no_data` (`no_records`); a failing record type is listed under `errors` (timeout, servfail, …), and an unreachable resolver ends the check after two questions. Bounds: 50 records per type, 2000 characters per TXT value.

- **C02 TLS** (S1.7, 2026-10-04): needs `dns` and connects to its first public address on port 443 with SNI, so nothing is resolved twice and a private answer is never connected to. Reports `verified`, the protocol, cipher and ALPN, the chain (length and subjects, Python 3.13+), and the certificate: names (SANs, wildcard flag), validity and days left, serial, SHA-256 fingerprint, key type/size/curve and signature algorithm. Verification is never disabled; when it fails the certificate is read through a second, unverified connection and the result says so (`forensic: true`, `verified: false`). A bad certificate is `ok` with `failures` (`expired`, `not_yet_valid`, `hostname_mismatch`, `untrusted`, …); nothing listening on 443 is `no_data` (`refused`); timeouts and handshake errors are `error`s with their reason. Skipped (`no_public_address`) when DNS found nothing it may connect to. Bounds: 100 names, 200 characters per name. A serial number that is zero or negative (RFC 5280 forbids it; a few old authorities issued such certificates, and `cryptography` warns that a future release will refuse to load them) is read anyway and recorded as `serial_positive: false`, with the host page saying so, instead of a console warning; a certificate that is presented but cannot be parsed at all is an `error` with the reason `certificate_unreadable`, never "valid" and never "no certificate".

- **C03 HTTP** (S1.8, 2026-10-04): needs `dns`; requests `https://host/` (redirects followed one screened hop at a time, at most 5) and `http://host/` once without following, both through the egress client at the addresses DNS found. Reports status, the redirect chain (status, location, IP per hop), the final URL (HTTPS or not, downgrade, foreign host), `Server` / `X-Powered-By`, the six security headers (absent is explicit `null`), every response header (60 max), every cookie's name and flags (`Secure`, `HttpOnly`, `SameSite`, prefix, session) — **never its value** — the page title, body size (read up to 512 KB, flagged when cut) and timing. `http_port80` says whether plain HTTP redirects to HTTPS or serves in clear text. If HTTPS cannot be reached (`https_error`: refused, timeout, `tls_verification_failed`, …) plain HTTP is the fallback; a redirect that is blocked (private target, port other than 80/443) or fails keeps the evidence gathered so far (`redirect_incomplete`). No web server on either port is `no_data`; timeouts are `error`s. Politeness: two requests per host (an alias for a hosted service is asked once or twice more by the takeover check, C08), our own User-Agent, no credentials, `robots.txt` is not consulted (a single `GET /` is what any visitor sends).

- **C04 IP location and C06 reverse DNS** (S2.1, 2026-10-04; one check, `ip`): needs `dns` and looks up its screened addresses (at most 8) in the **offline DB-IP Lite city and ASN databases** — country, region, city, coordinates, AS number and organisation, with the database type and build date. Nothing is sent to a third party. `flask datasets update` installs them into `DATASETS_DIR` (default `var/datasets/`): current month then previous month from `download.db-ip.com`, the `wp-statistics` mirror as city fallback; gzip bombs and oversized files are stopped, the file must be a recent database of the right kind that answers a probe lookup, it replaces the old one atomically, and source and SHA-256 go into `datasets.json`. Workers pick up a replaced file without a restart. Missing data is `unavailable` (`datasets_missing`, with the command to fix it), addresses the database does not know are `no_data`. Each address carries a **network hint** (C07, partly): CDN and anycast networks (Cloudflare, Fastly, Akamai, Edgio, CloudFront and others) are recognised by AS number, by a CDN name in the host's CNAME chain, or by its reverse DNS, and flagged `edge` — for such addresses the location is where the address is announced, not where data is processed (observed with the real database: Cloudflare and Edgecast anycast addresses geolocate to Toronto, Sydney and London). The host page says so; the location rule (S2.4) must read that flag. Reverse DNS (up to 5 PTR names per address) stops after the first resolver timeout. **Attribution:** "IP geolocation by DB-IP.com" (CC BY 4.0) is linked in the page footer, on the IP section and in the CLI output. Not built: the optional keyless API fallback (ipwho.is) and the iptoasn ASN fallback.

- **C05 Ports and CVEs** (S2.2, 2026-10-04; check `ports`): needs `dns` and follows `ip` (it reads that check's CDN hint when there is one but does not need the location databases). Each screened public address (at most 4 per host) is looked up at the provider `PORTS_PROVIDER` selects: `auto` is the **Shodan host API** when `SHODAN_API_KEY` is set and the keyless **Shodan InternetDB** otherwise; `shodan` and `internetdb` force one (`shodan` without a key is `unavailable: missing_api_key`, never a silent downgrade) and `off` disables the check. Nothing is sent to the assessed host. Per address the result lists ports (with transport, product and version from Shodan), CVE IDs (with CVSS score, summary and Shodan's `verified` flag from Shodan; InternetDB has IDs only), tags, the host names and CPEs the provider lists, owner and ASN, and **when the provider observed it** (`last_update` for Shodan, the fetch time otherwise). It is a snapshot of what a scanner saw: a port that is not listed is not evidence that it is closed, and an address the provider knows nothing about is `no_data` (`no_information`), never "no open ports". **Attribution:** every address carries `shared_infrastructure` (the network hint says CDN/edge, the provider tags it `cdn`, its owner is a known CDN, or more than five host names share it — these ports and CVEs describe the shared network, not this host's servers), `hostname_supported` (the provider lists this host name for the address) or `ip_only`, with the reasons as stable codes (`attribution_basis`); a cloud VM is not "shared". The hosts table shows ports and CVEs only for the addresses that speak for the host, and `Shared infrastructure` otherwise. **Politeness and cost:** one rate limiter per provider shared by all worker threads (`SHODAN_RATE_PER_SECOND` default 1, `INTERNETDB_RATE_PER_SECOND` default 2); hosts that share an address are checked at the same time, so they take turns per address and the later ones read the first one's answer from the cache; definitive answers (`ok`, `no_data`) are cached per provider and address in `provider_cache` for `PORTS_CACHE_HOURS` (default 24, at most 720) and swept after 30 days — errors and quota problems are never cached; after a failure that every further address would share (rejected key, quota, rate limit, timeout) the remaining addresses are not asked (`not_asked`). **Secrets:** the Shodan key travels in the query string, so every log record is rewritten as it is created (`key=`, `token=`, `Authorization`, the password in `scheme://user:password@host` URLs, also inside tracebacks), provider exceptions are mapped to reason codes and never carry the URL, and the key is never part of a result. **Terms:** InternetDB is free for non-commercial use only (the host page says so when it is the source); Shodan host lookups of known addresses do not use query credits. **Verification status:** the InternetDB fixture is a recorded real answer and the keyless chain DNS → ports ran live. The Shodan host parser was written from Shodan's documented response shape (its fixture is built from the documentation); a verification scan with the configured key then parsed one real answer correctly (ports, product and version, CVE ids with CVSS score and summary, tags, host names, owner and ASN for badssl.com's address), but no raw response has been recorded as a fixture yet — that waits for the owner's say-so.

- **C14 CVE enrichment** (S4.3, 2026-10-06; part of the `ports` check, not a check of its own): the CVE ids a provider reports for an address are looked up in two public files that `flask datasets update` installs, **CISA's Known Exploited Vulnerabilities catalogue** (`kev.json`: vendor, product, the date it was added and whether CISA knows of use in ransomware campaigns) and **FIRST's EPSS scores** (`epss.sqlite`: the estimated probability of exploitation within 30 days and its percentile, about 380,000 CVEs). Nothing about the scan is sent: the lookups are local, so which software a vendor runs does not leave the network. Each CVE gets `kev` and `epss` (or `null`), the list is sorted known-exploited first, then by EPSS, then by CVSS, and the result says what it was ranked by and as of when (`exploit_data`: `ranked_by`, `kev_as_of`, `epss_as_of`, `stale`, `problem`). A download is accepted only if it is complete, bounded, of the expected shape, recent and contains Log4Shell (a CVE every real release has); it replaces the installed file atomically, so a failed update damages nothing. Nothing installed is `ranked_by: none` (never "not exploited"); data older than a week is flagged. NVD (CVSS and descriptions for the CVEs that have none) is not built: it needs a request per CVE and would send them out. The rule `CVE_OBSERVED` (v2) turns this into a severity.

- **C08 Subdomain takeover** (S4.1, 2026-10-07; check `takeover`, needs `dns`): when a host is an alias (CNAME) for a hosted service whose names a stranger can claim, the check looks at the one thing that decides it, whether the name behind the alias is unclaimed. **Two ways it shows.** A service where anyone can register a name that does not exist (Microsoft Azure's namespaces, AWS Elastic Beanstalk, Discourse: `dns`) is judged from the DNS check alone: the alias ends in a name that does not exist (`claimable`; no request at all). A service that answers an unknown host with a page of its own (GitHub Pages, Heroku, Amazon S3 and its website endpoints, Netlify, Vercel, Surge, Pantheon, Tilda: `page`) is asked for the host's home page, over plain HTTP first and over HTTPS only when HTTP got no answer, through the egress gate (the addresses DNS found, screened and IP-pinned, certificates verified, 64 KB, three redirects at most, the host's own name in `Host`), and the status and the text are compared with what the service shows for an unclaimed name: `unclaimed` (the signature was seen with that status), `in_use` (the service answered something else; not a guarantee) or `not_tested` with the reason (nothing could be read). A host that is not an alias for a listed service costs no request, the page is never stored (only which signature it showed) and nothing is claimed anywhere. **The ruleset** (`app/checks/takeover_services.py`) is adapted from can-i-take-over-xyz (CC BY 4.0, `fingerprints.json` of 2025-02-08) and is not a copy: the source leaves most CNAME targets empty and several of its texts are out of date, so 30 services were asked about names nobody can own and the ones that behaved as written on 2026-10-07 were kept (8 page services, 3 DNS services), without any the source calls "Not vulnerable". `claim` says how open the claim is (`open`: anyone may register the name; `conditional`: the service checks something first, the source's "edge case"). **What it cannot see:** a service that sends an unknown host to HTTPS with a certificate for another name (Ghost, Help Scout, Webflow's `proxy-ssl`): the egress gate never turns certificate verification off, so the page cannot be read and the result is `not_tested: tls_verification_failed`, never "in use"; services that answer an unknown host with a generic error (Shopify, Zendesk and Freshdesk: Cloudflare's "origin DNS error") or a bot challenge (Tumblr, Read the Docs, ReadMe), which cannot be told from an ordinary failure; anything not on the list; and abandonment that is not reached through a CNAME (a delegated zone, a record for an address). Netlify answers a client that prefers HTML with another page than one without a preference, so both texts are listed and the check asks like a browser. Rule `TAKEOVER_LIKELY` (High; confidence High when anyone may claim the name and the page was seen, Medium otherwise) replaces `DANGLING_CNAME` for the names it covers. 13 live tests (`pytest -m live tests/checks/test_takeover_live.py`) repeat the probe against the real services.

- **C12 TLS versions and suites** (S4.4, 2026-10-07; check `tls_protocols`, needs `dns`): the server is asked one question per handshake, offering only that version (TLS 1.2, 1.3, 1.1, 1.0) or only that kind of suites (suites without encryption or without authentication), and nothing is sent after the handshake. Five handshakes per host go to the first screened public address, 5 s each and 60 s at most; a port that refuses ends after the first question (`no_data: refused`). The certificate is not verified for these (the TLS check does that): the question is what the server is willing to negotiate, not who it is, and nothing from the connection is trusted. Each answer is `accepted` (with the version and the suite the server chose, and whether that suite gives forward secrecy), `rejected` (an alert, or it hung up), `unknown` (a timeout or a network problem) or `not_testable` (this client cannot offer it). **What the standard library can and cannot ask:** Python's `ssl` on today's OpenSSL (3.0 here) cannot offer SSLv2, SSLv3, RC4, DES, 3DES or export suites at all, and offers TLS 1.0 and 1.1 only with the security level lowered (`@SECLEVEL=0`), so those are listed in `not_tested` together with the OpenSSL that asked: `rc4.badssl.com` and `3des.badssl.com` therefore answer nothing, which is not "safe". A server that completes no handshake at all is an `error` (`no_handshake`, `not_tls` or `timeout`) that no rule judges, so a server that refuses every question never looks like one that supports nothing. SSLv3, RC4, 3DES and the strength of Diffie-Hellman parameters need a dedicated tester (testssl.sh or sslyze as an optional external tool is still open; S4.8 adds the SSL Labs cross-check). **Rules:** `TLS_LEGACY_PROTOCOL` (Medium: TLS 1.0 or 1.1 accepted next to the current versions), `TLS_NO_MODERN_PROTOCOL` (High: only old versions accepted), `TLS_NO_TLS13` (Informational), `TLS_NULL_OR_ANONYMOUS_SUITES` (High) and `TLS_NO_FORWARD_SECRECY` (Low: in a TLS 1.2 handshake the server *chose* a suite without forward secrecy; merely accepting one is common, github.com does, and is not reported). A question that timed out or could not be put is never taken for a refusal. 8 live tests (`pytest -m live tests/runner/test_tls_protocols_live.py`) repeat it against badssl.com's test servers and github.com.

**Shipped at domain level:**
- **C20 Email security** (S2.3a, 2026-10-05; check `email`, scope domain, runs once per scan): the mail-related DNS records of the assessed domain, asked of `EGRESS_DNS_RESOLVERS`; only the MTA-STS policy is fetched over HTTPS, through the egress gate (screened address, IP-pinned, verified certificate, 64 KB, three redirects at most). **MX** (null MX per RFC 7505 is recognised as "does not receive mail"; hosts of well-known mail platforms are named: Google Workspace, Microsoft 365, Proofpoint, Mimecast, Infomaniak, Hostpoint, …). **SPF**: the record, its final `all` (the verdict of the `redirect` target when there is no `all`, RFC 7208 6.1), the DNS lookups an evaluator would spend following `include` and `redirect` (at most 10 fetches; `lookups_complete: false` when the walk stopped early), the sending services it names (SendGrid, Mailchimp, Salesforce, …) and problems (`multiple_records`, `no_all`, `too_many_lookups`, `ptr_used`, unknown terms). **DMARC**: policy, subdomain policy, `pct`, alignment, `rua`/`ruf`, problems (invalid policy or `pct`, several records). **DKIM**: 25 common selector names are tried (Google, Microsoft 365, Mailchimp, SendGrid, Zoho, Proton, Fastmail, generic); usable keys are listed with type, size (RSA bits via `cryptography`) and test mode, **revoked** selectors (empty key — example.com answers every selector that way) apart. Selectors cannot be enumerated, so "no selector found" is stated as exactly that. **MTA-STS** (DNS record and policy: mode, `max_age`, `mx`), **TLS-RPT** and **BIMI** (records only; the logo URL is shown as text, never fetched or linked). Each part says whether it was found, absent, or *could not be asked* (`found: null` with the error) — a timeout is never shown as "not found"; two failures in a row end the check as an `error`, NXDOMAIN is `no_data`; a 40-second budget bounds the whole run. Judging the findings (a missing DMARC record, `p=none`, weak keys) is S2.4. Checked live against example.com, github.com, google.com, admin.ch and microsoft.com (about two seconds each); that run showed that a wildcard-revoked zone must not list 25 "keys" and that `admin.ch` decides its SPF through a `redirect`.
- **C21 Registration** (S2.3b, 2026-10-05; check `registration`, scope domain): registrar (name and IANA id), registration, expiry and last-change dates, EPP status flags (with `transfer_locked` derived from them), the name servers at the registry and DNSSEC (from `secureDNS`: `delegationSigned`, or the presence of DS/key data), asked of the domain's registry over **RDAP** through the egress gate. The registry is found through **IANA's bootstrap file** (`data.iana.org/rdap/dns.json`, 71 KB, 1,203 TLDs, cached 24 h) for the *registrable* domain (public suffix list, ICANN part only: `shop.example.co.uk` → `example.co.uk`; a private suffix such as `blogspot.com` is not a registry). **The bootstrap lacks several important ccTLDs** — `.ch`, `.li`, `.de`, `.io`, `.at`, `.eu` — so a small supplemental table (`.ch` and `.li` → `rdap.nic.ch`, `.de` → `rdap.denic.de`, `.io` → `rdap.identitydigital.services`, all answering on 2026-10-05) fills the gap; `.at` and `.eu` have no reachable RDAP and say `no_data: no_rdap_service` with the advice to look the registration up by hand. Registries differ in what they publish and the check shows exactly that: `.ch` gives no dates at all (`dates_published: false`; registrar name from the jCard `org`), `.de` only a last-change date and DNSSEC keys, Verisign (.com) everything. Dates are normalised to UTC; days to expiry and age are worked out when the page is built, never stored, so a cached answer does not go stale. **Privacy:** registrant, technical and abuse entities, addresses, phone numbers and e-mails are never read, so they cannot be stored (tested with a body full of them). Typed: unknown TLD `no_data` (`no_rdap_service`), unknown domain `no_data` (`not_found`), rate limit/refusal `unavailable`, server errors, timeouts, blocked destinations and an unreadable bootstrap `error`. Answers (and the bootstrap) are cached per domain for 24 h in `provider_cache`; failures never. **The domain name is sent to the registry**: `EXTERNAL_DOMAIN_LOOKUPS` switches this lookup (and, with S2.3c, hstspreload.org and Have I Been Pwned) off individually. Checked live against example.com, github.com, admin.ch, bbc.co.uk, denic.de, nic.io and a TLD without RDAP (about 0.9 s each); the fixtures are recorded real registry answers (2026-10-05).
- **C22 DNSSEC** (2026-10-05): no check of its own. The registry's `secureDNS` flag (or the presence of DS/key data) is part of C21 (`dnssec: true/false/null`), because it is the registry that publishes the delegation signature.
- **Name servers and CAA** (S2.3c, 2026-10-05; check `domain_dns`, scope domain; the "CAA and NS diversity" of the roadmap): the NS records of the registrable domain, each server's addresses (at most 8 servers, 4 addresses each), the **operators** (registered domain of the server names: `nsone.net`, `awsdns-32.org`) and the **networks** (IPv4 /24, IPv6 /48) they span. `too_few` (under two servers), `single_network` and `unresolvable` are problems; one operator is only a *note*, because the big DNS providers are redundant by design (a live run flagged google.com, admin.ch, adobe.com and example.com as "single point of failure" before this was changed). **CAA** follows RFC 8659: the closest name that has any record decides, climbing from the assessed name to the zone; an error on the way up makes the answer unknown instead of guessing from a parent; issuers (parameters dropped), `issuewild`, `iodef` and "no authority may issue" (`issue ";"`) are summarised. Absent CAA is a fact (any authority may issue), judged in S2.4.
- **C23 security.txt** (S2.3c, 2026-10-05; check `security_txt`): fetched through the egress gate from `/.well-known/security.txt` then `/security.txt` of the domain, then the same on `www.` when the domain itself has no web server (three redirects at most per fetch, 64 KB, 60 s in all; a domain that redirects to `www` is followed and the hops are reported). A 200 page is only a security.txt if it has a recognised field and is not HTML. The RFC 9116 fields are kept (contacts, expiry, encryption, policy, acknowledgments, canonical, hiring, languages; free text and comments are dropped), PGP-clearsigned files are unwrapped and flagged `signed`. Problems: `missing_contact`, `missing_expires`, `multiple_expires`, `invalid_expires`, `expired`, `not_plain_text`, `not_https`, `offsite` (served from another domain), `canonical_mismatch`. A live run found that GitHub and Google write the expiry with a **lower-case `z`** (legal in RFC 3339 but rejected by Python's parser — handled) and that GitHub regenerates its `Expires` on every request (a rolling 30 days, so a short expiry is not a warning). Absent is `no_data` (`no_security_txt`); when the domain's own server could not be asked at all it is an `error`, not an absence.
- **C25 HSTS preload** (S2.3c, 2026-10-05; check `hsts_preload`): `hstspreload.org/api/v2/status` — `preloaded`, `pending`, `rejected`, `removed` or `unknown` (not on the list; a fact, not a failure), cached 24 h. The domain name is sent to hstspreload.org (`EXTERNAL_DOMAIN_LOOKUPS`).
- **C24 Public breach history** (S2.3c, 2026-10-05; check `breaches`): Have I Been Pwned's `breaches?domain=` endpoint (no key), asked for the registrable domain, one request per two seconds across all threads, cached 24 h. Kept: name, domain, breach and added dates, account count, data classes, and HIBP's own flags (verified, fabricated, sensitive, retired, **spam list** — scrapes such as LinkedInScrape2023 —, malware, stealer log), newest first (20 at most; the total is counted). HIBP's descriptions are HTML written by a third party and are never stored. None known is `no_data` (`no_breach_known`) and the page says finding none proves nothing. **Attribution:** the data is CC BY 4.0, so the section and the README link to haveibeenpwned.com. The domain name is sent to HIBP (`EXTERNAL_DOMAIN_LOOKUPS`). The recency rule (`BREACH_RECENT_MONTHS`) belongs to S2.4.
All four were run live against github.com, google.com, admin.ch, adobe.com and example.com (0.2-1.0 s each) and their pages were looked at with those real results; fixtures are recorded real answers (2026-10-05).

## 2. web-check handlers we do not adopt

| Handler | Decision |
|---|---|
| carbon, quality, social-tags, social-presence, linked-pages, sitemap, robots-txt, trace-route | **Skip** — no bearing on where/who/security; trace-route is also active probing |
| rank, archives | **Later** (R5, context only) |
| get-ip, location, ports | **Merged** into C04 / C05 |

## 4. Rule set

Findings come from versioned rules in `app/rules/`: one pure function per rule (stored check results in, findings out), so a rule can be refined and re-run over old scans (`flask findings evaluate`). Severity and confidence are separate; provider data keeps its own severity next to ours. **The full list (id, when it fires, what it says, what to do) is generated from the code: [rules.md](rules.md).**

Built in S2.4: **34 rules** — 16 per host (TLS, HTTP headers and cookies, DNS, location), 2 per public address (risky ports, CVE leads) and 16 for the domain (email, registration, breach history, security.txt, CAA, name servers). What was decided while building them:

- `TLS_INVALID`: expired, untrusted or not yet valid → High; a hostname mismatch alone → Medium. Weak keys (RSA < 2048, EC < 224, DSA) and weak signatures (SHA-1, MD5) are High; a certificate expiring within 30 days is Low, within 7 days Medium (an expired one is `TLS_INVALID`, not "expires soon").
- Header rules judge the host's *own* response only (a redirect to another host says nothing about the site): `HSTS_*` on an HTTPS response; `CSP_MISSING`, `XCTO_MISSING` and `FRAME_PROTECTION_MISSING` on an HTML response with a status below 400, not on a JSON API or an error page. `frame-ancestors` in the CSP counts as clickjacking protection.
- `COOKIE_INSECURE` needs a session-like name (`sid`, `session`, `PHPSESSID`, ...); CSRF cookies are exempt from `HttpOnly`; the `__Host-` and `__Secure-` prefixes imply `Secure`. Cookie values are never stored.
- `NO_HTTPS` is not raised when HTTPS failed on the certificate or the TLS handshake: that is `TLS_INVALID`'s business. Confidence is high when the HTTPS port refused the connection, medium otherwise.
- `RISKY_PORT_EXPOSED` and `CVE_OBSERVED` belong to the *address*: one finding per address (and port), listing the hosts of the scan that resolve to it. Shared infrastructure (CDN edges, multi-tenant hosting) is skipped. CVE ids from a banner are leads, not proof, so they are Informational with medium confidence at best.
- `SPF_PERMISSIVE`: `+all` High; `?all` or no `all` term Medium. `DMARC_POLICY_NONE` is Low. One DNS operator is a note (`NS_NOT_REDUNDANT`, Low), fewer than two name servers Medium.
- `DANGLING_CNAME` means the alias target does not exist (Medium, low confidence: whether it can be claimed is not tested). The takeover-fingerprint test and a High rating stay in R4.
- Beyond the plan, because the checks already collect the facts: `SPF_INVALID`, `DMARC_INVALID`, `DOMAIN_NOT_LOCKED`, `SECURITY_TXT_INVALID`, `CAA_MISSING`, `NS_NOT_REDUNDANT`, `DNS_PRIVATE_ADDRESS`.
- Not built: `TLS_LEGACY_PROTOCOL` and `KEV_LISTED_CVE` (R4, they need a protocol probe and the KEV feed). `COLLECTION_INCOMPLETE` is not a rule: coverage is a statement about the *scan* (S2.5's coverage line), not a finding about the vendor.

Two owner-specified rules:

| Rule | Trigger | Severity |
|---|---|---|
| `LOCATION_OUTSIDE_EU_CH` | a public IP of the host is located outside the allowed area (EU-27 + EEA + CH) | **High**; Medium with low confidence for CDN/anycast IPs (edge only) |
| `PUBLIC_BREACH_HISTORY` | HIBP lists a breach of the vendor's own service (fabricated, spam-list and retired entries ignored; one finding per breach) | **Medium; High if the breach date is within 24 months** (`BREACH_RECENT_MONTHS`) |

**Data-location policy (rule `LOCATION_OUTSIDE_EU_CH`).**
- Allowed area = EU-27 + EEA (IS, LI, NO) + CH, configurable (`DATA_LOCATION_ALLOWED`, ISO codes) so adequacy countries such as GB or JP can be added.
- The rule uses the *country* from DB-IP; the city is context only (accuracy for server IPs is poor).
- One finding per host. It fires if *any* resolved public IP is outside the area and lists the IPs and countries.
- CDN/anycast IPs (ASN hint list) show the edge, not the data centre, so they raise Medium with low confidence instead of High — otherwise every Cloudflare- or CloudFront-fronted vendor would be a High finding.
- No location data (database missing, IP not in the database) gives the rule nothing to read: no finding, and the assessment page says that the data is missing. It is never "clean"; the coverage line (S2.5) reports it.
- The finding can be accepted with a reason and a review date ([S2.6](roadmap.md)).

**Summary cards (S2.5).** The cards of the assessment page read what the checks stored, so a check that says where or who should be wired in `app/service/summary.py`: *Where* ← `ip` (country, city, the CDN/edge flag); *Who* ← `ip` (network, AS number, kind), `domain_dns` (DNS operators), `email` (MX providers, SPF senders), `registration` (registrar); *Secure* ← the findings and `finding_disposition`; coverage ← the status of every check and the discovery counts. A check that did not answer is "not determined" in the card, never "none".

## 6. How to add a check

A check is one module in `app/checks/` that returns a typed outcome; the registry, scheduler, storage, rules and UI pick it up.

```python
class Check(Protocol):
    key: str                                  # "tls"
    scope: Literal["host", "domain"]
    needs: tuple[str, ...]                    # e.g. ("dns",): runs only if those are ok
    def run(self, ctx: CheckContext) -> CheckOutcome: ...

# CheckOutcome(status="ok|no_data|unavailable|error|skipped", reason_code, data: dict, findings: list[FindingDraft])
```

Checklist: module + unit test with fixtures (no network) + catalogue row + (if the result can be judged) a rule in `app/rules/` with a test in `tests/rules/` that feeds it the output of the real check, then `uv run python -m app.rules.docs` to regenerate [rules.md](rules.md). If the check says *where* or *who*, add it to the summary cards (`app/service/summary.py`).
